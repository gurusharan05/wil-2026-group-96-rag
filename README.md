# International Student RAG — Three-University Project

## 1. Project Overview

The **International Student Assistant** is a Retrieval-Augmented Generation (RAG) application designed to help international students explore Master of Data Science programs and find information about studying in Australia.

The project covers:

- RMIT University
- The University of Melbourne
- Monash University
- Australia-wide student visa work conditions and workplace rights

The application combines structured course comparisons with semantic search and source-grounded answers generated by a local language model.

## 2. Main Features

### Compare Courses

The course comparison feature uses deterministic filtering over:

`data/structured/university_courses.csv`

Users can compare published course information, including:

- University and course name
- Course code
- International tuition fee
- Fee year and fee basis
- Course duration
- Campus location
- Available intakes

Fee figures retain their published year and fee basis because universities may report tuition costs differently. They should not automatically be interpreted as directly comparable annual fees.

### Ask a Question

The question-answering feature uses Retrieval-Augmented Generation (RAG).

The process is:

1. The user enters a question.
2. The application searches ChromaDB for relevant knowledge-base chunks.
3. The question is embedded using the configured Ollama embedding model.
4. Relevant evidence is passed to the language model.
5. The model generates an answer grounded in the retrieved evidence.
6. Retrieved evidence is displayed to help users understand the basis of the answer.

The application is designed to avoid unsupported answers when relevant evidence is unavailable.

## 3. Technology Stack

| Component | Technology |
|---|---|
| Programming language | Python |
| User interface | Streamlit |
| Large language model | Qwen3 14B (`qwen3:14b`) |
| Embedding model | Qwen3 Embedding 0.6B (`qwen3-embedding:0.6b`) |
| Language model runtime | Ollama |
| Vector database | ChromaDB |
| Structured data processing | Pandas |
| PDF text extraction | pypdf |
| Testing | pytest and custom evaluation scripts |

The language model and embedding model are separate components. Qwen3 generates answers, while the embedding model converts questions and documents into vectors for semantic retrieval.

## 5. Prerequisites

Install the following before setting up the application:

- Python 3.11 recommended for a fresh environment
- Ollama
- Git, if cloning the repository
- Sufficient disk space and memory for the selected language model

Python dependencies are listed in `requirements.txt`.

## 6. Installation and Setup

### Step 1 — Open the project directory

Open a terminal in the project root, where `app.py`, `config.py`, and `requirements.txt` are located.

### Step 2 — Create a virtual environment

```bash
python3 -m venv venv
```

Activate it on macOS or Linux:

```bash
source venv/bin/activate
```

Confirm that the environment is active:

```bash
which python
python --version
```

The Python path should point to the project's `venv` directory.

### Step 3 — Install dependencies

```bash
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

### Step 4 — Check Ollama

Ensure Ollama is installed and running.

List the locally available models:

```bash
ollama list
```

The project configuration expects these models:

```text
qwen3:14b
qwen3-embedding:0.6b
```

If either model is missing, download it:

```bash
ollama pull qwen3:14b
ollama pull qwen3-embedding:0.6b
```

You can check the configured model names in `config.py`.

## 7. Build or Rebuild the Knowledge Base

The raw documents are processed into text chunks, embedded, and stored in ChromaDB.

If the supplied `data/chroma_db/` database is present and valid, you generally do not need to rebuild it.

If the database is missing, incomplete, or needs to be rebuilt after changing the ingestion pipeline or source data, run the appropriate ingestion script from the project root:

```bash
PYTHONPATH=. python scripts/ingest_clean_v2.py
```

The ingestion script should read the supported files under `data/raw/`, generate document chunks and embeddings, and persist them in the configured ChromaDB directory.

**Important:** Rebuilding the database may replace or add records depending on the ingestion script's implementation. Check its collection-clearing and duplicate-ID handling before running it against an existing database.

## 8. Run the Application

Ensure the virtual environment is active and Ollama is running.

Start Streamlit:

```bash
python -m streamlit run app.py
```

Open the local URL printed in the terminal, usually:

`http://localhost:8501`

The application provides two main sections:

1. **Compare Courses** — compares the structured course dataset.
2. **Ask a Question** — retrieves relevant evidence from ChromaDB and generates an answer using Ollama.

The course comparison feature and the RAG question-answering feature serve different purposes and use different data-processing paths.

## 9. Test Retrieval

The retrieval test scripts help verify that questions return relevant knowledge-base evidence.

Run the general retrieval test:

```bash
PYTHONPATH=. python scripts/test_retrieval.py
```

A university-specific retrieval test is also available:

```bash
PYTHONPATH=. python scripts/test_rmit_retrieval.py
```

Use these tests after changing the ingestion pipeline, retrieval logic, metadata filters, or embedding configuration.

## 10. Evaluate Retrieval Performance

The evaluation script measures retrieval performance against a fixed set of questions.

Run:

```bash
PYTHONPATH=. python scripts/evaluate_retrieval.py
```

Evaluation results are saved under:

`evaluation/results/`

The metrics can include:

- **Source Hit@1:** Whether the top retrieved result contains the expected source.
- **Source Hit@3:** Whether the expected source appears within the top three results.
- **Source Hit@5:** Whether the expected source appears within the top five results.
- **Keyword Hit@k:** Whether expected answer keywords appear in the retrieved evidence within the top *k* results.
- **In-domain performance:** Retrieval performance for questions the knowledge base is intended to answer.
- **Out-of-domain rejection:** Whether questions unsupported by the knowledge base are appropriately rejected.

These metrics assess retrieval behaviour; they do not independently prove that every generated answer is factually correct.

Review the evaluation questions and results when making changes to the RAG pipeline.

## 11. Automated Tests

The `tests/` directory is reserved for automated checks of application components.

Tests can be added for:

- Configuration and data loading
- Course dataset validation
- Retrieval functions in `rag.py`
- University and topic routing
- ChromaDB integration
- Handling missing or irrelevant evidence
- Answer-generation behaviour

Once tests are implemented, run them with:

```bash
python -m pytest tests/ -v
```

The command will run the tests discovered by pytest. If the directory does not yet contain test cases, add them before relying on the result as evidence of application correctness.

## 12. Source Data and Reliability

The project uses source snapshots and structured data for its current knowledge base.

Some raw HTML files are project-created snapshots or paraphrased extracts rather than live copies of official webpages. They should not be represented as current official publications.

Before a final demonstration or deployment:

- Verify course details against the relevant university's official website.
- Verify student visa conditions against the Australian Department of Home Affairs.
- Verify workplace rights against the Fair Work Ombudsman.
- Refresh time-sensitive tuition fees, entry requirements, intake dates, and accommodation information.
- Record source URLs and the dates on which information was checked.
- Rebuild and evaluate the knowledge base if the underlying evidence changes.

The application is an informational student project, not a substitute for official immigration, legal, financial, or university advice.

## 13. Source Boundaries

Use the appropriate source for each information category:

| Information | Preferred source |
|---|---|
| RMIT course and university information | RMIT University |
| University of Melbourne course and university information | The University of Melbourne |
| Monash course and university information | Monash University |
| Student visa conditions | Australian Department of Home Affairs |
| Workplace rights and employment protections | Fair Work Ombudsman |
| Study and student-life information | Relevant official university or Study Australia resources |

The RAG system should answer using retrieved evidence and clearly indicate when that evidence does not provide the requested information.

## 14. Development Workflow

When modifying the project:

1. Activate the virtual environment.
2. Make the code or data changes.
3. Run syntax checks where appropriate.
4. Run the relevant retrieval tests.
5. Run the fixed evaluation after retrieval-related changes.
6. Test the Streamlit interface manually.
7. Review the changes before committing them to Git.

For example, check the main Python files with:

```bash
python -m py_compile app.py config.py rag.py
```

Then run the application:

```bash
python -m streamlit run app.py
```

## 15. Git and Team Collaboration

Before committing changes:

```bash
git status
git diff
```

Commit only the intended source files and documentation.

Do not commit:

- The virtual environment (`venv/`)
- Python cache files (`__pycache__/` and `*.pyc`)
- API keys, passwords, or other secrets
- Unnecessary temporary files and local backups

Follow the team's agreed approach for sharing the knowledge base and evaluation outputs. Ensure teammates have the required Ollama models and Python dependencies.

## 16. Project Limitations

- Answers depend on the completeness and quality of retrieved evidence.
- University fees and accommodation information can change.
- Different fee years and fee bases may prevent direct fee comparisons.
- Local model inference speed depends on the computer and model size.
- Retrieval metrics do not guarantee answer correctness.
- The knowledge base is limited to the sources included in the project.
- The application does not automatically guarantee that its source snapshots are up to date.
